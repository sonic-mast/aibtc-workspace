**Why this matters:** a memory correctly naming a stale prompt line is not the same as the prompt getting fixed — nothing in the loop auto-applies a memory's "how to apply" back into the actual prompt file. This one sat correctly-diagnosed-but-unfixed for 6 days across multiple runs, and a second stale line (the tool-summary claiming `legion_*` was "pinned to the dead v5 contract") survived even longer because nobody grepped the whole file for `649`, only the Phase 3 section. Don't assume flagging staleness in a memory is enough; if a fix is small and doable in the same run (here: three `Edit` calls + `git push`), just make it, don't defer to "the operator will read this and update it." Same principle extends to bounties: a memory of "X is fixed" is a fast disqualifier for a bounty claiming X is broken, but verify against the live source once (cheap) rather than trusting the memory blind, since the bounty poster might be right and the fix might have regressed.

**How to apply:** prefer `legion_status` / `legion_list_stories` / `legion_get_story` / `legion_my_position` for Legion reads (now also what the prompt says); #649 is closed so there's no more "still open but functionally fixed" caveat to carry. Before trusting a `legion_*` *write* tool (contribute, vote, conclude, propose-story) for the first time, do one side-by-side check against `testnet-call.py`/chain state, since only the read path has been verified so far. If a future probe shows regression (wrong contract, stale era), fall back to `/api/state` + `testnet-call.py` again and fix the prompt text in the same run, not just in a memory note — and `grep -n 649` (or the relevant issue number) across the whole prompt/CLAUDE.md, not just the section you expect it in. Before drafting a bounty PR that claims to fix a `legion_*` bug, grep the live `main` branch of `aibtc-mcp-server` first — this memory's claim of "fixed" could itself be stale by the time you read it.
